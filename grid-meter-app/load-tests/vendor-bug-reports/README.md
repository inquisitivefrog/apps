# Vendor bug-report evidence archive

This directory exists because moving from a single-instance-per-service test
configuration to a real HA configuration (3 instances per service) surfaced a
case where a clustering technology may not behave the way its own
documentation says it should (see `kafka/` below). When that happens, the
right outcome is a real upstream bug report — which needs preserved,
organized evidence, not scrollback. This directory is that evidence archive.
It is **not** the place for the written narrative/theory of a finding — that
belongs in `docs/` (e.g. `docs/testing-strategy-ha-supplement.md` for the
Kafka investigation) so it goes through this project's normal doc review.
This directory holds the raw material that narrative cites.

## Layout

```
vendor-bug-reports/
  <technology>/              # kafka, redis, postgres, ... one per suspect technology
    NOTES.md                 # index of runs + links to the authoritative docs/ narrative
    runs/
      <timestamp>-<label>/   # one directory per test run's full raw evidence
      <timestamp>-<label>.txt  # a single-file run (e.g. a standalone diagnostic snapshot)
                                # gets just a file, not a directory, if that's all it produced
```

- **One subdirectory per technology** under suspicion (`kafka/`, `redis/`,
  `postgres/`, ...) — add a new one the same way if a different service's HA
  behavior comes into question later (Traefik, the app's own Kafka producer,
  etc.) rather than assuming this stays Kafka-specific.
- **`NOTES.md` per technology** is a short, chronological index: what each
  run in `runs/` was, its date, its verdict, and a pointer to the `docs/`
  narrative doc that has the actual analysis. It is deliberately NOT a
  duplicate of that narrative — one source of truth for the "why," this file
  only for the "where's the evidence for that."
- **`runs/`** holds the raw material: captured logs, `kafka-configs.sh
  --describe` output, JMX counter dumps, before/after snapshots, script
  transcripts — whatever a specific test run produced. Multi-file runs get
  their own timestamped directory; a single-file run (e.g. one diagnostic
  snapshot) can just be a timestamped file directly under `runs/`.

## Filing status tracking

Each technology's `NOTES.md` tracks whether a vendor bug report has actually
been filed yet, and against what ticket/issue number once one exists. As of
2026-08-29, Kafka's investigation has a JIRA account pending approval — filing
is blocked on that, evidence-gathering isn't.

## Why this isn't just `load-tests/results/`

`load-tests/results/` (JMeter's own output) is disposable, regenerated by
every load-test run, and never meant to be preserved run-over-run — matching
`testing-strategy.md`'s framing of load tests as "manual/nightly, never
blocks a PR." This directory is the opposite: it exists specifically because
some of what's captured here needs to survive across sessions, reboots, and
Docker resets, as the actual evidence base for a real report to a third
party. Treat it like `status/`'s dated session logs, not like scratch
output — durable by design, not cleaned up between runs.
