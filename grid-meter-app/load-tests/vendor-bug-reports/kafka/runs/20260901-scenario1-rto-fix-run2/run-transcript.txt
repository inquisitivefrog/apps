SCENARIO 1: Tolerate the ACTUAL partition leader's loss (dynamically determined, real RTO measured)
================================================================
docs/testing-strategy-ha-supplement.md flagged this as still open: the original version of
this scenario stopped kafka-2 unconditionally, regardless of whether kafka-2 actually led any
partition this test's traffic uses -- with 3 partitions spread across all 3 brokers (each
partition has its own leader) and messages keyed by meterId, a fixed broker choice risks
silently testing nothing at all if this run's meter happens to hash to a partition kafka-2
doesn't lead. It also never measured real RTO, just a fixed 5s sleep before sending traffic.

Determining which partition THIS meter's traffic actually lands on, via an offset diff around
a canary write, rather than assuming or hashing it ourselves (Kafka's own partitioner is the
only source of truth for this).

This meter's traffic lands on partition 2
Current leader of partition 2: broker 1 (kafka-1)

Killing kafka-1 -- the broker THIS test's traffic actually depends on, not an
assumed one -- and measuring real RTO (polling for a new leader) concurrently with sending
traffic, so some of it genuinely spans the live election window rather than only running

Results
================================================================
Scenario 1 (actual partition leader loss, partition 2, kafka-1 -> 2):
  20 succeeded, 0 failed (of 20); measured RTO: 14028ms
  PASS: zero impact from the actual leader's loss, as RF=3 promises.
Scenario 2 (two-broker quorum loss, 150s):
  HTTP level:     10 succeeded, 0 failed (of 10) -- NOT the real evidence, see below.
  Durability:     0 of 10 landed while still below quorum; 0 more landed after recovery.
  REAL DATA LOSS: 10 reading(s) never reached the readings table --
  delivery.timeout.ms (undeclared default: 120000ms) expired before quorum was restored.
  Accepted per docs/resilience-scope.md's redo-path decision: a simulated meter reading has
  no real downstream consequence if lost, so this is observed (deliveryFailureCounter, the
  'reading delivery failures' alert) rather than prevented via an outbox+reconciler.
Scenario 3 (rolling maintenance):        30 succeeded, 0 failed (of 30)
  PASS: zero downtime across the full rolling restart.
